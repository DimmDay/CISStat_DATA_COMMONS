## 1. СТАТУС

Proposed.
Настоящий ADR подготовлен как черновая заготовка по итогам анализа экспертного фидбека к ТЗ на цифровую реконструкцию платформы CISStat. Решение подлежит рассмотрению и утверждению Architecture Review Board в соответствии с GOV-003.

## 2. КОНТЕКСТ

Текущая архитектура платформы построена преимущественно на синхронных запросах (API, Knowledge Graph, поиск). Обновление данных (например, загрузка нового показателя национальной статистической системой) не имеет формализованного механизма распространения изменений между зависимыми компонентами платформы — Knowledge Graph, поисковым индексом, TS Analysis, AI-сервисами.

Современные государственные и статистические платформы всё чаще опираются на событийную модель для согласованного, асинхронного распространения изменений между подсистемами.

## 3. ПРОБЛЕМА

Отсутствие событийного слоя приводит к следующим рискам:

- рассинхронизация состояния Knowledge Graph, поискового индекса и аналитических сервисов после обновления данных;
- отсутствие единого механизма уведомления зависимых сервисов об изменениях;
- необходимость точечных интеграций между каждой парой сервисов вместо единого механизма публикации событий;
- сложность добавления новых потребителей событий (например, нового AI-сервиса) без изменения источника события.

## 4. РЕШЕНИЕ

Принято решение ввести самостоятельный архитектурный слой — **Event Platform**, обеспечивающий асинхронное распространение событий между компонентами платформы.

```
Event Broker (публикация/подписка)
        │
        ▼
     Events
        │
        ▼
  Subscriptions
        │
        ▼
  Notifications
```

Типовой сценарий распространения события:

```
НСО загрузила новый показатель
        │
        ▼
  создаётся событие
        │
        ▼
Knowledge Graph обновляется
        │
        ▼
индекс OpenSearch обновляется
        │
        ▼
TS Analysis получает событие
        │
        ▼
LLM Cache обновляется
```

## 5. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ РЕШЕНИЯ

### 5.1 Event as First-Class Integration Mechanism
Событие является основным механизмом распространения изменений между компонентами платформы, дополняя (но не заменяя) синхронные API-вызовы.

### 5.2 Publisher–Subscriber Decoupling
Источник события не должен обладать информацией о конкретных потребителях. Подписка и уведомление реализуются независимо от источника, что соответствует принципу Interoperability by Design (ARC-018).

### 5.3 Infrastructure Agnostic Event Broker
В соответствии с ARC-007 (Infrastructure Agnostic) и ARC-014 (No Vendor Lock-In) архитектурный слой именуется **Event Streaming Platform**, а не привязывается к наименованию конкретного продукта. Конкретный брокер сообщений (например, Kafka-совместимая реализация или иной открытый стандарт AMQP/MQTT-класса) рассматривается как референсная реализация, подлежащая замене без изменения архитектурного контракта.

### 5.4 Semantic Event Schema
Каждое событие должно иметь машиночитаемую, версионируемую схему и быть связано с соответствующим Knowledge Object (MM-000), что обеспечивает трассируемость изменений данных до конкретного события.

### 5.5 Events Do Not Bypass Metadata Gate
Событие, инициирующее обновление Knowledge Graph, не освобождает данные от требований ARC-017 (Metadata Before Data). Событие может быть создано только после прохождения данными Metadata Validation Gate, определённого в ADR-002.

## 7. ПОСЛЕДСТВИЯ ПРИНЯТИЯ РЕШЕНИЯ

Положительные:
- согласованное обновление всех зависимых компонентов платформы;
- упрощение добавления новых потребителей событий без изменения источника;
- основа для реактивных AI-сценариев (например, автоматическое обновление LLM Cache);
- снижение числа точечных интеграций между сервисами.

Потенциальные ограничения:
- необходимость проектирования схем событий и их версионирования;
- дополнительная операционная сложность (мониторинг очередей, обработка ошибок доставки);
- необходимость согласования Event Platform с Metadata Validation Gate (ADR-002), чтобы события не создавались до завершения проверки метаданных.

## 9. РЕАЛИЗАЦИЯ

- реестр схем событий (Event Schema Registry), версионируемый и машиночитаемый;
- Event Broker (референсная реализация, открытый стандарт, без vendor lock-in);
- механизм подписки (Subscriptions) для Knowledge Graph, OpenSearch, TS Analysis, AI Platform;
- журнал доставки и трассируемость событий в соответствии с ARC-010 (Everything is Traceable).

## 10. СООТВЕТСТВИЕ СТАНДАРТАМ

- CloudEvents (рекомендуется как открытый стандарт формата событий);
- JSON Schema / JSON-LD для описания структуры события;
- Open Standards First (ARC-011).

## 11. СВЯЗАННЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ

- ADR-002 — Enterprise Data Fabric (источник событий на входе);
- ADR-003 — API Platform Decomposition (Webhooks как внешний канал уведомлений);
- ADR-005 — AI Platform (потребитель событий для обновления LLM Cache).

## 12. ОТКРЫТЫЕ ВОПРОСЫ (для рассмотрения ARB)

- Выбор референсной реализации Event Broker с обоснованием отсутствия vendor lock-in.
- Формат канонической схемы событий (CloudEvents vs собственный формат).
- Политика retention и повторной доставки событий.
