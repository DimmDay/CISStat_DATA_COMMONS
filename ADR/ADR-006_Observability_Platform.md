## 1. СТАТУС

Proposed.
Настоящий ADR подготовлен как черновая заготовка по итогам анализа экспертного фидбека к ТЗ на цифровую реконструкцию платформы CISStat. Решение подлежит рассмотрению и утверждению Architecture Review Board в соответствии с GOV-003.

## 2. КОНТЕКСТ

В текущей редакции ТЗ наблюдаемость (observability) упоминается исключительно как нефункциональное требование, без выделения самостоятельного архитектурного слоя, компонентов и владельца.

При растущем числе сервисов платформы (Data Fabric, Knowledge Graph, API Platform, Event Platform, AI Platform) отсутствие единого архитектурного подхода к метрикам, логам и трассировке запросов затрудняет диагностику, аудит и подтверждение соответствия принципу ARC-010 (Everything is Traceable).

## 3. ПРОБЛЕМА

Отсутствие выделенного слоя наблюдаемости приводит к следующим рискам:

- разрозненный, несогласованный мониторинг в разных сервисах платформы;
- невозможность сквозной трассировки запроса через несколько слоёв (Data Fabric → Knowledge Graph → API → AI Platform);
- сложность диагностики инцидентов в распределённой архитектуре;
- отсутствие единого источника данных для аудита производительности и надёжности, требуемого ARC-010.

## 4. РЕШЕНИЕ

Принято решение выделить самостоятельный архитектурный слой — **Observability Platform**, обеспечивающий единый подход к метрикам, распределённой трассировке и логированию для всех компонентов платформы.

```
Observability Platform
   │
   ├── Metrics (референсная реализация: Prometheus-совместимая система)
   ├── Dashboards (референсная реализация: Grafana-совместимая система)
   ├── Distributed Tracing (референсная реализация: Tempo-совместимая система)
   ├── Log Aggregation (референсная реализация: Loki-совместимая система)
   └── OpenTelemetry (обязательный открытый стандарт инструментирования)
```

## 5. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ РЕШЕНИЯ

### 5.1 OpenTelemetry as Mandatory Instrumentation Standard
Все сервисы платформы обязаны инструментироваться в соответствии с открытым стандартом OpenTelemetry для метрик, трассировки и логирования. Данное требование является обязательным и не подлежит замене проприетарными SDK.

### 5.2 Reference Implementations, Not Mandates
Конкретные продукты для хранения метрик, визуализации, трассировки и логов (в тексте фидбека — Prometheus, Grafana, Tempo, Loki) рассматриваются как **референсные реализации**, соответствующие открытым стандартам, а не как обязательные архитектурные компоненты, в соответствии с ARC-007 (Infrastructure Agnostic) и ARC-014 (No Vendor Lock-In). Допускается замена любого из этих компонентов эквивалентной открытой или переносимой альтернативой без изменения архитектурного контракта.

### 5.3 End-to-End Traceability of Requests
Каждый запрос, проходящий через несколько архитектурных слоёв (Data Fabric, Knowledge Graph, API Platform, Event Platform, AI Platform), должен сохранять единый идентификатор трассировки (trace context) на всём пути, что является технической реализацией принципа ARC-010.

### 5.4 Observability as Knowledge Object Domain
Конфигурации мониторинга, дашборды и правила алертинга рассматриваются как цифровые артефакты репозитория (GOV-002 §1.7) и подлежат версионированию наравне с прочими компонентами платформы.

## 7. ПОСЛЕДСТВИЯ ПРИНЯТИЯ РЕШЕНИЯ

Положительные:
- единая, сквозная трассируемость запросов через все архитектурные слои;
- ускорение диагностики инцидентов;
- независимость от конкретного поставщика инструментов мониторинга;
- соответствие ARC-010 на техническом уровне.

Потенциальные ограничения:
- необходимость обязательного инструментирования всех новых и существующих сервисов;
- дополнительные затраты на инфраструктуру хранения метрик, логов и трассировок при росте числа сервисов.

## 8. ВЛИЯНИЕ НА АРХИТЕКТУРУ

| Домен                    | Влияние     |
|---------------------------|-------------|
| Technology Architecture   | Высокое     |
| Infrastructure Architecture | Высокое   |
| Security Architecture      | Среднее (аудит доступа к логам) |
| Application Architecture   | Среднее (обязательное инструментирование) |

## 9. РЕАЛИЗАЦИЯ

- обязательное подключение OpenTelemetry SDK ко всем сервисам платформы;
- единый формат trace context, распространяемый через API Platform и Event Platform;
- выбор референсных реализаций для метрик, дашбордов, трассировки и логов с обоснованием отсутствия vendor lock-in;
- политика хранения и ротации логов и метрик, согласованная с требованиями Security by Design (ARC-012).

## 10. СООТВЕТСТВИЕ СТАНДАРТАМ

- OpenTelemetry;
- Open Standards First (ARC-011);
- Infrastructure Agnostic (ARC-007).

## 11. СВЯЗАННЫЕ АРХИТЕКТУРНЫЕ РЕШЕНИЯ

- ADR-002, ADR-003, ADR-004, ADR-005 — все компоненты которых подлежат обязательному инструментированию Observability Platform.

## 12. ОТКРЫТЫЕ ВОПРОСЫ (для рассмотрения ARB)

- Итоговый выбор референсных реализаций для метрик, логов, трассировки и дашбордов.
- Политика доступа к логам и метрикам, содержащим потенциально чувствительные данные.
- Порядок ретроспективного инструментирования существующих компонентов (ПАК ИАП, ЕИАС, СУЗ-СОД).
