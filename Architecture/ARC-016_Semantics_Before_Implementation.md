# ARC-016 — Semantics Before Implementation
Отвечает на вопрос «в какой последовательности должна разрабатываться платформа?»

## 1. Purpose

Настоящий принцип устанавливает обязательную последовательность проектирования платформы CIS Data Commons.
Ни одна модель данных, API, программный компонент, пользовательский интерфейс или сервис не должны проектироваться до определения их семантической модели.

Смысл объекта всегда определяется раньше его технической реализации.

---

# 2. Problem Statement

Во многих информационных системах архитектура строится в обратном порядке:

Code
→ Database
→ API
→ Documentation
→ Metadata

Такой подход приводит к возникновению многочисленных проблем:

- различная трактовка одних и тех же понятий;
- несовместимые модели данных;
- невозможность автоматической интеграции;
- сложность внедрения ИИ;
- появление большого количества "локальных" сущностей;
- дублирование информации;
- отсутствие единой терминологии.

Для межгосударственной статистической платформы подобная архитектура неприемлема.

---

# 3. Principle Statement

Любая сущность платформы должна быть определена сначала на семантическом уровне, после чего допускается разработка моделей данных, API и программной реализации.

Архитектурная последовательность является обязательной.

---

# 4. Canonical Development Order

Для всех компонентов платформы используется следующий порядок разработки.

1. Business Concept
2. Knowledge Object
3. Ontology
4. Metadata Model
5. Logical Data Model
6. Physical Data Model
7. API Contract
8. Service Implementation
9. User Interface

Каждый следующий уровень обязан ссылаться на предыдущий.

# 6. Consequences

Следствием применения принципа являются:

- единая терминология;
- единая семантическая модель;
- отсутствие противоречий между API;
- автоматическая генерация моделей данных;
- возможность построения графа знаний;
- совместимость со стандартами SDMX, DDI, RDF, OWL, XBRL и Schema.org;
- поддержка AI Native Architecture.

---

# 7. Design Rules

Каждый новый объект обязан иметь:

- определение в онтологии;
- описание в Knowledge Graph;
- принадлежность к Knowledge Domain;
- связь с Knowledge Object;
- машиночитаемое семантическое описание.

До выполнения этих условий разработка программной реализации не допускается.

---

# 8. Compliance Requirements

Каждый ADR, Data Model, API Specification и компонент платформы должны содержать ссылки:

- `ONT-*`
- `MM-*`
- ARC-016

При отсутствии указанных ссылок объект считается не соответствующим архитектуре платформы.

---

# 9. Exceptions

Исключения допускаются только:

- при миграции существующих систем;
- при интеграции внешних решений;
- по решению Architecture Review Board.

Каждое исключение должно быть оформлено отдельным ADR.

---

# 10. Rationale

Данный принцип обеспечивает переход от Data-Centric Architecture к Knowledge-Centric Architecture.

В результате семантика становится первичным архитектурным активом платформы, а программная реализация рассматривается как одно из возможных представлений знаний.

Это обеспечивает долговременную устойчивость архитектуры, упрощает интеграцию национальных статистических систем, повышает интероперабельность и создает основу для использования интеллектуальных агентов, Knowledge Graph и технологий искусственного интеллекта.

# 12. Compliance Checklist

Перед разработкой любого нового компонента необходимо подтвердить:

- [ ] Определен бизнес-концепт.
- [ ] Создан Knowledge Object.
- [ ] Определена онтология.
- [ ] Определены метаданные.
- [ ] Разработана модель данных.
- [ ] Определен API-контракт.
- [ ] Добавлены связи в Knowledge Graph.
- [ ] Выполнена реализация.
- [ ] Создан пользовательский интерфейс.
