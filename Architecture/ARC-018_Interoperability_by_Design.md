# ARC-018 — Interoperability by Design

# 1. Purpose

Настоящий принцип устанавливает обязательное требование, согласно которому интероперабельность является встроенным свойством архитектуры платформы CIS Data Commons.

Совместимость между компонентами, национальными статистическими системами, международными организациями и интеллектуальными сервисами должна обеспечиваться архитектурными решениями на этапе проектирования, а не посредством последующих интеграционных доработок.

---

# 2. Problem Statement

Традиционный подход к разработке информационных систем предполагает создание автономных решений с последующей интеграцией посредством адаптеров, ETL-процессов и специализированных шлюзов.

Подобный подход приводит к:

- появлению множества точечных интеграций;
- высокой стоимости сопровождения;
- дублированию данных;
- несовместимости моделей;
- усложнению миграции;
- ограниченной масштабируемости;
- снижению качества данных.

Для международной статистической платформы подобная архитектура недопустима.

---

# 3. Principle Statement

Каждый компонент платформы должен проектироваться как совместимый с другими компонентами без необходимости разработки специальных механизмов интеграции.

Интероперабельность является обязательным нефункциональным свойством любого архитектурного элемента.

---

# 4. Levels of Interoperability

Платформа обеспечивает интероперабельность на следующих уровнях.

## Organizational

- единые процессы управления;
- единая терминология;
- единые правила публикации.

---

## Semantic

- единые определения понятий;
- единые онтологии;
- единый Knowledge Graph.

---

## Structural

- единые модели данных;
- единые идентификаторы;
- единые схемы сериализации.

---

## Technical

- REST API;
- OpenAPI;
- JSON;
- JSON-LD;
- GraphQL (при необходимости);
- OGC API (для геоданных).

---

## Infrastructure

- Docker;
- Kubernetes;
- Linux;
- Cloud Neutral Deployment.

---

# 5. Open Standards First

Все интерфейсы платформы должны строиться на открытых международных стандартах.

Приоритет использования:

1. Международный стандарт.
2. Общепринятый отраслевой стандарт.
3. Собственный стандарт CIS Data Commons.

Использование закрытых протоколов допускается только при отсутствии открытых аналогов.

---

# 6. Canonical Standards

Для различных категорий объектов устанавливаются базовые стандарты.

| Категория             | Стандарт            |
|-----------------------|---------------------|
| Statistical Data      | SDMX                |
| Microdata             | DDI Lifecycle       |
| Financial Reporting   | XBRL                |
| Metadata              | SIMS / ESMS / ESQRS |
| Linked Data           | RDF                 |
| Ontology              | OWL                 |
| Controlled Vocabulary | SKOS                |
| Dataset Catalogue     | DCAT                |
| Semantic Markup       | Schema.org          |
| API                   | OpenAPI 3.1         |
| Identity              | URI / IRI           |
| Provenance            | PROV-O              |
| Serialization         | JSON / JSON-LD      |

---

# 7. Canonical Data Exchange

Каждый сервис должен поддерживать каноническое представление данных.
Внутреннее хранение может отличаться.
Внешний контракт должен оставаться стабильным.

---

# 8. API Interoperability

Каждый API обязан:

- использовать OpenAPI;
- иметь машиночитаемую спецификацию;
- использовать единые правила именования;
- поддерживать версионирование;
- использовать единые схемы ошибок;
- поддерживать безопасную аутентификацию.

---

# 9. Semantic Interoperability

Каждый Knowledge Object должен:

- иметь URI;
- иметь семантическое описание;
- быть представлен в Knowledge Graph;
- иметь связи с онтологией;
- использовать общие словари терминов.

---

# 10. Metadata Interoperability

Все метаданные должны быть совместимы с международными стандартами.

Приоритет:

1. SDMX
2. DDI
3. SIMS
4. ESMS
5. ESQRS
6. Schema.org
7. DCAT

---

# 11. AI Interoperability

Все компоненты платформы должны быть доступны интеллектуальным агентам через стандартизированные интерфейсы.
Для этого используются:

- OpenAPI;
- MCP;
- JSON-LD;
- Knowledge Graph;
- семантические описания ресурсов.

---

# 12. Version Compatibility

Изменения не должны нарушать совместимость существующих клиентов без документированного процесса миграции.
При несовместимых изменениях создается новая версия контракта.

---

# 13. Architecture Consequences

Применение настоящего принципа обеспечивает:

- отсутствие vendor lock-in;
- независимость от технологий реализации;
- возможность подключения новых государств;
- интеграцию с международными организациями;
- масштабируемость;
- долгосрочную сопровождаемость;
- возможность автоматической интеграции AI-сервисов.

---

# 14. Compliance Requirements

Каждый новый компонент должен подтвердить:

- использование открытых стандартов;
- поддержку канонической модели данных;
- наличие машиночитаемого контракта;
- наличие семантического описания;
- совместимость с Knowledge Graph;
- поддержку глобальной идентификации объектов.

При отсутствии любого из перечисленных требований компонент не может считаться соответствующим архитектуре платформы.

---

# 15. Exceptions

Использование нестандартных решений допускается только:

- при отсутствии международного стандарта;
- при миграции исторических систем;
- по решению Architecture Review Board.

Все исключения оформляются отдельным ADR.

---

# 16. Rationale

Интероперабельность рассматривается как фундаментальное свойство архитектуры, обеспечивающее устойчивое взаимодействие всех компонентов платформы независимо от используемых технологий.

Совместимость достигается за счет единой семантики, единых моделей данных, открытых стандартов и единых контрактов взаимодействия.

# 18. Compliance Checklist

Перед вводом компонента в эксплуатацию необходимо подтвердить:

- [ ] Используются открытые международные стандарты.
- [ ] Реализован канонический API.
- [ ] Поддерживаются глобальные идентификаторы.
- [ ] Определена семантическая модель.
- [ ] Обеспечена совместимость с Knowledge Graph.
- [ ] Реализована поддержка машиночитаемых метаданных.
- [ ] Подготовлена OpenAPI-спецификация.
- [ ] Выполнена проверка архитектурного соответствия.
