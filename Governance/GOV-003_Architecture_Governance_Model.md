# GOV-003 — Architecture Review Board

## Какой вопрос решает данный документ?

**Кто обладает полномочиями принимать окончательные архитектурные решения, как разрешаются архитектурные разногласия между доменами платформы и каким образом обеспечивается единообразие архитектуры CIS Data Commons?**

---

## 1. Назначение

Настоящий документ определяет состав, полномочия, ответственность и порядок работы **Architecture Review Board (ARB)** — постоянно действующего коллегиального органа архитектурного управления платформой **CIS Data Commons**.

Architecture Review Board обеспечивает целостность архитектуры платформы, предотвращает расхождение архитектурных решений между отдельными подсистемами, доменами знаний и командами разработки, а также утверждает стратегические изменения архитектуры.

ARB является высшим архитектурным органом проекта и действует в рамках Governance Framework.

---

## 2. Цели

Architecture Review Board создается для достижения следующих целей:

- обеспечение единства архитектуры платформы;
- предотвращение архитектурной деградации;
- контроль соблюдения архитектурных принципов;
- согласование изменений, затрагивающих несколько доменов;
- разрешение архитектурных конфликтов;
- утверждение архитектурных решений, имеющих долгосрочные последствия;
- поддержание архитектурной совместимости всех компонентов платформы.

---

## 3. Полномочия ARB

Architecture Review Board имеет исключительное право:

- утверждать Architecture Decision Records (ADR);
- утверждать изменения Architecture Principles (ARC);
- утверждать изменения Enterprise Architecture;
- рассматривать междоменные архитектурные конфликты;
- утверждать архитектурные стандарты (STD);
- утверждать корпоративные модели знаний (MM);
- утверждать изменения верхнеуровневой онтологии;
- утверждать Canonical Models платформы;
- отклонять архитектурные решения, противоречащие утвержденным принципам.

Решения ARB являются обязательными для исполнения всеми командами проекта.

---

## 4. Область ответственности

ARB рассматривает исключительно архитектурные вопросы.

К компетенции ARB не относятся:

- управление проектами;
- приоритизация бизнес-функциональности;
- оперативная разработка;
- планирование релизов;
- эксплуатационная поддержка.

---

## 5. Состав Architecture Review Board

Минимальный состав ARB:

- Chief Architect (председатель);
- Enterprise Architect;
- Data Architect;
- Metadata Architect;
- Ontology Architect;
- Platform Architect;
- Security Architect.

При необходимости в заседаниях могут участвовать приглашенные эксперты без права голоса.

---

## 6. Кворум

Заседание считается состоявшимся при участии не менее двух третей постоянного состава.

Для принятия решения требуется квалифицированное большинство голосов.

Изменения следующих объектов требуют единогласного решения:

- Architecture Constitution;
- Upper Ontology;
- Knowledge Object Metamodel;
- Canonical Identifier Standard.

---

## 7. Принципы принятия решений

ARB руководствуется следующими принципами:

1. Architecture First.
2. Semantics Before Implementation.
3. Metadata Before Data.
4. Interoperability by Design.
5. Open Standards First.
6. Cloud Neutrality.
7. Canonical Source Principle.

---

## 8. Canonical Authority

Каждый архитектурный домен имеет единственный источник архитектурной истины (Canonical Authority).

Если возникает противоречие между несколькими доменами, решение принимается исходя из полномочий соответствующего владельца домена до рассмотрения вопроса ARB.

ARB рассматривает только те случаи, которые невозможно разрешить на уровне владельцев доменов.

---

## 9. Рассмотрение архитектурных конфликтов

Основанием для рассмотрения являются:

- конфликт между архитектурными принципами;
- конфликт между моделями данных;
- конфликт между онтологиями;
- конфликт между API;
- конфликт между подсистемами;
- конфликт между стандартами;
- предложение изменить утвержденную архитектуру.

Каждый конфликт оформляется как Request for Architecture Decision и сопровождается соответствующим ADR.

---

## 10. Процесс принятия решения

```text
Issue
   │
   ▼
Domain Owner Review
   │
   ▼
Architecture Review Board
   │
   ▼
Architecture Decision Record
   │
   ▼
Repository Update
   │
   ▼
Implementation
```

Все принятые решения документируются посредством Architecture Decision Record.

---

## 11. Прозрачность решений

Каждое решение ARB должно:

- иметь уникальный идентификатор ADR;
- содержать обоснование;
- содержать анализ альтернатив;
- иметь ссылки на связанные требования;
- иметь ссылки на затронутые модели;
- иметь ссылки на связанные архитектурные принципы;
- быть опубликовано в репозитории.

---

## 12. Трассируемость

Каждое решение ARB должно иметь трассируемость до:

- требований (REQ);
- архитектурных принципов (ARC);
- стандартов (STD);
- моделей знаний (MM);
- онтологий (ONT);
- моделей данных (DM);
- API;
- компонентов платформы.

---

## 13. Взаимодействие с ADR

ARB является органом утверждения Architecture Decision Records.
Правила подготовки, жизненный цикл и структура ADR определяются документом **ADR/README.md**.
Настоящий документ определяет только полномочия ARB как органа архитектурного управления и не дублирует требования стандарта ADR.
