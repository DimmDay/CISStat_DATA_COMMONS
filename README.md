## 1. О чём этот репозиторий

CISStat DATA COMMONS — главный архитектурный репозиторий программы реконструкции портала Статкомитета СНГ и построения платформы **CISStat Unified Data & Knowledge Platform**. Философия программы: **«Единая точка входа в мировую статистику»**.

Это репозиторий **знаний, а не программного кода**. Он хранит архитектуру, стандарты, метамодель, онтологии, архитектурные решения и правила работы проекта в формате docs-as-code: каждый артефакт — документ с уникальным идентификатором, версией, статусом и машиночитаемыми метаданными, проходящий автоматические проверки CI.

Ключевая идея зафиксирована в ADR-001: репозиторий сам является **Enterprise Knowledge System** — базой знаний проекта. Каждый документ — **Knowledge Object** с постоянным идентификатором и связями с другими объектами. Из этой базы знаний в дальнейшем вырастает граф знаний платформы (Knowledge Graph).

## 2. Контекст программы

Программа реконструкции объединяет четыре действующие системы Статкомитета СНГ в единую платформу данных и знаний:

| Система | Адрес | Назначение |
|---|---|---|
| БД «Статистика СНГ» (ПАК ИАП) | new.cisstat.org | Публичный портал, витрина показателей |
| ЕИАС | eias.cisstat.org/biportal | BI/OLAP-аналитика, дашборды |
| СУЗ | suz.cisstat.org | База знаний, методология (XWiki) |
| СОД | catalog.cisstat.org | Каталог связанных открытых данных (RDF/SPARQL) |
| CISStat DataTime Lab | datasetup.ru | Анализ временных рядов, DSS (внешний сервис) |

Целевая архитектура — **Граф знаний СНГ (CIS Statistics Knowledge Graph)** по модели Google Data Commons (Place - StatisticalVariable - Observation) с каноническими идентификаторами **CIS-ID**, разметкой Schema.org и публикацией данных в международных стандартах: SDMX, DDI, SIMS/ESMS/ESQRS, XBRL, RDF/SPARQL/SKOS/XKOS.

Стратегия внедрения — эволюционная интеграция (strangler fig): существующие системы продолжают работать, новый слой API и графа знаний «обволакивает» их без остановки. Полное описание — в Техническом задании на реконструкцию (Этап 1 программы, внешний документ).

Роль настоящего репозитория — **архитектурно-управленческий фундамент программы** (Фаза 1): зафиксировать принципы, решения, семантику и правила до начала реализации.

## 4. Система идентификации артефактов

Каждый документ — Knowledge Object с постоянным идентификатором:

| Префикс | Каталог | Назначение | Состояние |
|---|---|---|---|
| GOV-xxx | Governance/ | Нормативные документы, правила проекта | 3 документа |
| ADR-xxx | ADR/ | Архитектурные решения | 7 решений + стандарт ведения |
| ARC-xxx | Architecture/ | Принципы и видение архитектуры | 8 документов + state-файл |
| MM-xxx | Metamodel/ | Метамодель знаний | 8 документов |
| ONT-xxx | Ontology/ | Онтологии, формальная семантика | 8 документов |
| STD-xxx | Standards/ | Стандарты: манифесты, идентификация | 2 стандарта |
| DM-xxx | Data Models/ | Прикладные модели данных | план |
| API-xxx | OpenAPI/ | API-контракты | план |
| KG-xxx | Knowledge Graph/ | Артефакты графа знаний | план |
| Portal-xxx | Portal/ | Презентационный слой | план |

Правила идентификации (STD-002, стандарт Knowledge Object Identity):

- **Object Identity** (например, ARC-016) — никогда не меняется;
- **Persistent URI** (например, <https://knowledge.cisstat.org/id/ARC-016>) — никогда не меняется;
- **Version** (SemVer) — меняется при каждой содержательной правке;
- **Location** (путь в Git) — может меняться.

Метаданные документа описываются манифестом по стандарту **STD-001 (KOMS)**: id, title, version, status, owner, authors, relationships, domain, tags, license и др.

## 6. Текущее состояние и приоритеты

Актуальное состояние проекта фиксируется в **Architecture/PROJECT_STATE.md** (разделы: миссия, текущая фаза, статусы архитектуры, приоритеты, план работ, риски, критерии успеха). README намеренно не дублирует эти данные - они меняются, а state-файл обновляется при каждом существенном изменении.

Сводно на текущий момент: фундамент знаний построен (governance, принципы, 7 ADR, метамодель, онтология, стандарты, CI-контур); каталоги DM-xxx, API-xxx, KG-xxx, Portal-xxx ожидают наполнения в следующих фазах.

## 7. Как работать с репозиторием

### 7.1 Ветвление (trunk-based)

- `main` — единственная постоянная ветка, хранит актуальную архитектуру.
- Прямые коммиты в `main` допускаются для владельца репозитория; для содержательных изменений - короткоживущая ветка + Pull Request.
- **Создание долгоживущих веток и слияние веток (merge) запрещены.** История должна оставаться линейной.
- Правило №1 governance: PR без документации недопустим - каждый PR сопровождается ADR, спецификацией или обновлением документации.

### 7.2 Коммиты

Формат: `type(scope): ID — суть изменения`

```text
docs(governance): GOV-002 — фиксация trunk-based политики ветвления
feat(ontology): ONT-002 — черновик статистической онтологии
ci(structure): выравнивание списка обязательных каталогов
chore(lint): устранение нарушений markdownlint
```

### 7.3 Локальные проверки (pre-commit)

```bash
git clone https://github.com/DimmDay/CISStat_DATA_COMMONS.git
cd CISStat_DATA_COMMONS
pip install pre-commit

# проверка всего репозитория перед коммитом
python -m pre_commit run --all-files
```

Хуки: trailing-whitespace, end-of-file-fixer, check-yaml/json/toml, check-merge-conflict, mixed-line-ending (LF), detect-private-key, markdownlint, yamllint, gitleaks.

Примечание для Windows: если команда `pre-commit` не находится в PATH, используйте `python -m pre_commit` - это эквивалентно и работает всегда.

### 7.4 CI-контур (GitHub Actions)

| Workflow | Что проверяет | Инструмент |
|---|---|---|
| 01-markdown.yml | Качество Markdown во всех документах | markdownlint-cli2 |
| 02-links.yml | Ссылки в документах | lychee |
| 03-yaml.yml | Качество YAML-файлов | yamllint |
| 04-manifest.yml | Валидация манифестов Knowledge Object | кастомная проверка |
| 05-structure.yml | Обязательная структура каталогов | bash |
| 06-security.yml | Отсутствие секретов в коде | gitleaks |

Если CI упал после вашего push: локально выполните `python -m pre_commit run --all-files`, исправьте указанные нарушения, закоммитьте снова. Обход проверок (`--no-verify`) не используется.

### 7.5 Требования к файлам

- Кодировка UTF-8 без BOM, переводы строк LF.
- Только текстовые форматы: Markdown, YAML, JSON, XML, PlantUML, Mermaid. Бинарные файлы не допускаются.
- Именование: `ПРЕФИКС-XXX_Название_артефакта.md` (подчёркивания вместо пробелов в именах файлов; каталоги - согласно фактической структуре раздела 3).
- Автоматические проверки конфигурации: .editorconfig, .markdownlint.yaml, .yamllint, .pre-commit-config.yaml, .gitleaks.toml.

## 8. Жизненный цикл изменений

```text
Идея → Issue (шаблоны в .github/ISSUE_TEMPLATE) → RFC (при необходимости)
     → Документ (ADR / ARC / STD / MM / ONT) → Ревью (CODEOWNERS, ARB)
     → Pull Request → Проверки CI → Merge → Обновление PROJECT_STATE.md
```

Статусная модель документа: Draft, Review, Approved, Deprecated, Superseded, Archived.

Важно: содержимое утверждённого ADR не удаляется и не редактируется задним числом (Immutable History, ADR_README раздел 4.3). Изменение решения оформляется новым ADR с пометкой Superseded by ADR-XXX.

## 9. Роли и ответственность

- **Architecture Review Board (ARB)** - высший орган архитектурного управления: утверждает ADR, разрешает конфликты, управляет жизненным циклом решений (ADR_README раздел 6).
- **Owner артефакта** - отвечает за актуальность и качество конкретного документа (указан в манифесте KOMS).
- **Авторы и ревьюеры** - закрепляются в .github/CODEOWNERS.
- **Контрибьюторы** - вносят изменения через Issue и Pull Request.

## 10. FAQ новичка

**Где код?**
Его пока нет - и это правильно. Репозиторий проходит ранние уровни зрелости (Governance, Architecture, Specifications). Код появится на уровне Implementation в каталогах Portal/, Services/, Infrastructure/ - и только после контрактов (OpenAPI) и моделей данных.

**Чем README.md отличается от REPOSITORY.md?**
README - входная точка и правила работы с репозиторием. REPOSITORY.md - концептуальный манифест «репозиторий как Enterprise Knowledge System», стратегический документ.

**Куда добавить новую модель данных?**
В каталог Data Models/ файлом DM-XXX_Название.yaml с манифестом по STD-001, через Pull Request. Порядок: модель данных до интерфейсов (принцип Data First).

**Можно ли исправить чужой утверждённый ADR?**
Нет. Решения неизменяемы: либо новая редакция, либо новый ADR со ссылкой Superseded by ADR-XXX.

**Почему у большинства документов статус Draft?**
Нормально для текущей фазы: фундамент зафиксирован, но формальное утверждение через ARB - предмет ближайших сессий согласования.

**CI упал - что делать?**
См. раздел 7.4: локальный прогон pre-commit, исправление по выводу, повторный коммит.
