## 1. О чём этот репозиторий

CISStat DATA COMMONS — корпоративный репозиторий архитектуры и знаний (Enterprise Architecture Repository) программы цифровой трансформации платформы CIS Data Commons / CISStat. Философия программы: **«Единая точка входа в мировую статистику»** (§2.1 TOR-004).

Это репозиторий **знаний, а не программного кода** (docs-as-code): принципы, решения, метамодель, онтологии, стандарты и правила работы проекта. Каждый артефакт — **Knowledge Object** с устойчивой идентичностью, семантикой, жизненным циклом и машиночитаемыми метаданными (§5.1 TOR-004); репозиторий сам рассматривается как граф знаний (ARC-015, §5.6).

С вступлением в силу TOR-004 (окончательная редакция) именно он является **первичным источником истины (Single Source of Truth)**: документ самодостаточен и спроектирован для последовательного чтения новой командой без обращения к внешним материалам. Настоящий README — входная точка в репозиторий: как устроено хранилище, где проходит граница между нормативной базой и историческим архивом, как работать с артефактами.

Ключевые решения TOR-004: шесть платформ, ранее находившихся в статусе Proposed (Enterprise Data Fabric, API Platform, Event Platform, AI Platform, Observability Platform, Security Platform), утверждены ARB и переведены в **Accepted**; все девять слоёв целевой архитектуры имеют статус Accepted (§7.1); начало работ по утверждённым слоям не требует повторного одобрения ARB (§6.4).

Правила обращения с архивом (§15.4 TOR-004):

- архив объясняет «почему»: обоснования, рассмотренные альтернативы, последствия решений;
- точные формулировки принципов для внешних презентаций цитируются из архива, а не реконструируются по памяти;
- при любом расхождении архива с TOR-004 приоритет имеет TOR-004 как более поздняя и единственная действующая редакция.

Формат хранения: TOR-004 ведётся вне репозитория в формате DOCX; в репозиторий вносится Markdown-конверсия в каталог `TOR/` (раздел 5) — бинарные файлы не допускаются (раздел 9.5).

## 3. Контекст программы

Программа объединяет действующие системы Статкомитета СНГ в единую платформу данных и знаний (§1.3, §3 TOR-004):

| Система | Адрес | Роль в целевой архитектуре |
|---|---|---|
| БД «Статистика СНГ» / ПАК ИАП | new.cisstat.org | Публичный фасад (Liferay); подключение данных через CDC на переходный период |
| ЕИАС | eias.cisstat.org/biportal | BI/OLAP-инструмент; сохраняется как data mart, синхронизируемый с графом |
| СУЗ-СОД | suz.cisstat.org, catalog.cisstat.org | Методология (XWiki) и семантический актив (RDF/OWL/SKOS/XKOS/ADMS, публичный SPARQL) — основа Knowledge Graph |
| CISStat DataTime Lab | — | Python/Streamlit-приложение анализа временных рядов (60% аналитика / 40% DSS); подключается изолированным сервисом (§9 TOR-004) |
| Портал CISStat_PORTAL | отдельный репозиторий | Реализуемая часть Presentation Layer (§7.10 TOR-004) |

Целевая модель графа знаний: **Place — StatisticalVariable — Observation — Provenance** с каноническими идентификаторами **CIS-ID** (§5.5, §7.4). Международные стандарты (SDMX, DDI, SIMS/ESMS/ESQRS, XBRL, Schema.org, RDF/SPARQL/SKOS/XKOS/ADMS, DCAT) реализуются как представления, генерируемые из единого графа, — без дублирования источников истины (§8 TOR-004); мост RDF ↔ SDMX — RDF Data Cube Vocabulary (W3C QB).

Стратегия внедрения — **Strangler Fig** (ARC-019, §12.1 TOR-004): поэтапное обволакивание действующих систем новым слоем API и графа знаний без единовременной остановки Liferay-портала, ЕИАС, СУЗ-СОД или CISStat DataTime Lab. Принятые ограничения: данные НСО — источник истины на переходный период; государства-участники сохраняют суверенитет над первичными данными; стек облачно-нейтральный, пригодный для on-premise (ARC-007).

## 4. Целевая архитектура: девять слоёв

Целевая архитектура (§7.1 TOR-004) состоит из **девяти слоёв**: пять образуют последовательный core-контур, четыре являются сквозными (cross-cutting) и применяются ко всему core-контуру. Все девять слоёв — Accepted; указанный стек — согласованная референсная реализация (ARC-014): конкретный продукт заменяется без изменения архитектурного контракта.

```text
Core:       Enterprise Data Fabric → Metadata Platform → Knowledge Graph → API Platform → Presentation Layer
Cross-cut:  Event Platform · AI Platform · Observability Platform · Security Platform
```

| Слой | Назначение | Референсный стек (§7 TOR-004) |
|---|---|---|
| Enterprise Data Fabric | Приём, приведение к канонической модели и валидация данных до графа; Metadata Validation Gate (ARC-017) | Airflow/Dagster, Debezium поверх Kafka, dbt, pandasDMX + XSLT, Great Expectations, MinIO |
| Metadata Platform | Единственный владелец методологии, качества, классификаторов (SKOS/XKOS), словарей, DSD, Data Contracts | Metadata Registry: PostgreSQL, схема SIMS/ESMS/ESQRS |
| Knowledge Graph | Семантическое ядро — расширение RDF/SPARQL-актива СОД до полной модели графа | Fuseki/GraphDB/Virtuoso, ClickHouse или Druid + Iceberg/Parquet, PostgreSQL (+PostGIS), OpenSearch, W3C QB |
| API Platform | Шесть интерфейсов: REST, GraphQL, SPARQL, SDMX API, MCP API, Webhooks | FastAPI/Spring Boot, Apollo или Hasura, Kong/APISIX, Camunda/Temporal, OAuth 2.1/OIDC |
| Presentation Layer | Headless UI поверх API Platform; Liferay — только источник контента для миграции | Next.js 14, TypeScript strict, Tailwind, Radix/shadcn/ui, BFF (NestJS/FastAPI) |
| Event Platform | Асинхронное распространение изменений; событие не создаётся в обход Validation Gate | Kafka или RabbitMQ, Redis |
| AI Platform | LLM Gateway, RAG, Prompt Registry, MCP Server; принцип «AI — ассистент, не автономный публикатор» | Подключаемые LLM, OpenSearch (векторный), Evaluation/Guardrails |
| Observability Platform | Единые метрики, трассировка, логи; сервис без инструментирования не вводится в эксплуатацию | OpenTelemetry, Prometheus, Grafana, Loki/ELK, Jaeger/Tempo |
| Security Platform | Единый IAM, федерация с системами НСО, секреты, Policy as Code, PKI, аудит | Keycloak, OIDC/OAuth 2.1/SAML 2.0, Vault, OPA |

Соответствие исторической терминологии (§1.6 TOR-004) — для чтения архивных документов и ранее написанного кода:

| Исторический термин | Источник | Единый термин (TOR-004) |
|---|---|---|
| CIS Statistics Knowledge Graph | TOR-001 | Knowledge Graph (§7.4) |
| Слои 1+2 Ingestion / Processing & Validation | TOR-001 | Enterprise Data Fabric (§7.2) |
| Слой 4 Service & API | TOR-001 | API Platform (§7.5) |
| Раздел 3.8 (стек UI/UX) | TOR-001 | §7.10 TOR-004 |
| ФТ-1…28, НФТ-1…6 | TOR-002 | FR-*/NFR-* (§11 TOR-004) |

Правило границ компонентов (§15.3 TOR-004): функциональность перемещает данные — Enterprise Data Fabric; обеспечивает качество и метаданные — Metadata Platform; связи и семантику — Knowledge Graph; точку доступа наружу — API Platform; асинхронное уведомление — Event Platform; работу с языковой моделью — AI Platform. Смешение ответственности нескольких слоёв в одном компоненте — повод для отдельного ADR, а не одностороннего решения на уровне кода.

## 6. Идентификация артефактов

Каждый артефакт — Knowledge Object. Минимальная структура объекта: Identity, Metadata, Semantic Definition, Lifecycle, Version, Relationships, Manifest, Representations, Provenance, Governance (§5.1 TOR-004). Контракт объекта — девять обязательных характеристик (§5.2): идентичность; тип по таксономии (§5.3); обязательные метаданные; правила версионирования; допустимые отношения (стандартные глаголы: implements, extends, references, dependsOn, derivedFrom и др.); жизненный цикл; сериализации (не менее одной машиночитаемой: JSON-LD, YAML, RDF); трассируемость (минимум одна связь вверх и вниз по иерархии); управление (владелец, ревьюер, утверждающий).

Жизненный цикл объекта: Draft → Proposed → Accepted → Implemented → Superseded/Deprecated → Archived.

CIS-ID — постоянный, человекочитаемый, версионируемый идентификатор (§5.5 TOR-004, принцип ARC-009). Три формы:

| Форма | Пример |
|---|---|
| Постоянный HTTP URI | <https://knowledge.cisstat.org/id/README> |
| URN | `urn:cid:ARC-016` |
| Графовый идентификатор | `cis:ARC-016` |

Пространства имён по типу объекта: `GOV`, `ARC`, `STP`, `REQ`, `ADR`, `DM`, `API`, `ONT`, `META`, `KG`, `SRV`, `PORT`, `INF`, `SEC`, `TEST`, `DOC`. Новые типы объектов создаются только через ADR (§5.3 TOR-004, Extension Rules). Домены знаний: Governance, Architecture, Requirements, Information, Metadata, Semantic, Integration, Analytics, AI, Portal, Infrastructure (§5.4) — по каждому явно поименованы Domain Owner, Architecture Owner, Metadata Owner, Data Steward.

Правила неизменности: Object Identity и Persistent URI никогда не меняются; Version (SemVer) меняется при каждой содержательной правке; Location (путь в Git) может меняться. Метаданные описываются манифестом по стандарту STD-001 (KOMS).

Примечание: в архивной части репозитория исторически используются префиксы `MM-*` и `STD-*`; целевая схема идентификации — §5.5 TOR-004; формальное сведение схем CIS-ID со STD-002 — открытый вопрос §13.2, оформляется отдельным ADR.

## 9. Как работать с репозиторием

### 9.1 Ветвление (trunk-based)

- `main` — единственная постоянная ветка, хранит актуальную архитектуру.
- Прямые коммиты в `main` допускаются для владельца репозитория; для содержательных изменений — короткоживущая ветка + Pull Request.
- **Создание долгоживущих веток и слияние веток (merge) запрещены.** История остаётся линейной.
- PR без документации недопустим: каждый PR сопровождается ADR, спецификацией или обновлением документации (Repository Governance, §6.3 TOR-004: Repository as Digital Twin, Single Source of Truth, запрет решений вне репозитория).

### 9.2 Коммиты

Формат: `type(scope): ID — суть изменения`

```text
docs(tor): TOR-004 — внесение Markdown-конверсии нормативного источника
docs(governance): GOV-002 — фиксация trunk-based политики ветвления
feat(ontology): ONT-002 — черновик статистической онтологии
ci(structure): выравнивание списка обязательных каталогов
```

### 9.3 Локальные проверки (pre-commit)

```bash
git clone https://github.com/DimmDay/CISStat_DATA_COMMONS.git
cd CISStat_DATA_COMMONS
pip install pre-commit

# проверка всего репозитория перед коммитом
python -m pre_commit run --all-files
```

Хуки: trailing-whitespace, end-of-file-fixer, check-yaml/json/toml, check-merge-conflict, mixed-line-ending (LF), detect-private-key, markdownlint, yamllint, gitleaks.

Примечание для Windows: если команда `pre-commit` не находится в PATH, используйте `python -m pre_commit` — эквивалентно и работает всегда.

### 9.4 CI-контур (GitHub Actions)

| Workflow | Что проверяет | Инструмент |
|---|---|---|
| 01-markdown.yml | Качество Markdown во всех документах | markdownlint-cli2 |
| 02-links.yml | Ссылки в документах | lychee |
| 03-yaml.yml | Качество YAML-файлов | yamllint |
| 04-manifest.yml | Валидация манифестов Knowledge Object | кастомная проверка |
| 05-structure.yml | Обязательная структура каталогов | bash |
| 06-security.yml | Отсутствие секретов в коде | gitleaks |

Если CI упал после push: локально выполните `python -m pre_commit run --all-files`, исправьте указанные нарушения, закоммитьте снова. Обход проверок (`--no-verify`) не используется.

### 9.5 Требования к файлам

- Кодировка UTF-8 без BOM, переводы строк LF.
- Только текстовые форматы: Markdown, YAML, JSON, XML, PlantUML, Mermaid. Бинарные файлы не допускаются — в том числе DOCX: TOR-004 вносится в репозиторий только как Markdown-конверсия.
- Именование: `ПРЕФИКС-XXX_Название_артефакта.md` (подчёркивания вместо пробелов в именах файлов; каталоги — согласно разделу 5).
- Конфигурация автоматических проверок: .editorconfig, .markdownlint.yaml, .yamllint, .pre-commit-config.yaml, .gitleaks.toml.
- Документы должны иметь машиночитаемую структуру и манифест (STD-001), совместимые с обработкой ИИ-агентами и RAG (§6.3 TOR-004).

## 10. Жизненный цикл изменений и ADR-процесс

```text
Идея → Issue (шаблоны в .github/ISSUE_TEMPLATE) → ADR (при новом решении)
     → Документ/артефакт → Ревью (CODEOWNERS) → Pull Request → CI
     → Merge → Обновление PROJECT_STATE.md
```

ADR-процесс (§6.2 TOR-004): Decision First (решение оформляется до начала реализации), One Decision — One ADR, Immutable History, Architecture Before Code, Explain Why. Статусы: Draft → Proposed → Accepted → Implemented, параллельно Superseded/Deprecated → Archived. Содержимое утверждённого ADR не редактируется задним числом; изменение решения — новый ADR с пометкой Superseded by ADR-XXX.

Пока проект ведёт один человек, все роли ARB совмещаются им; требование кворума и единогласия временно исключено (§6.1 TOR-004) — исключение переоформляется отдельным ADR по мере роста команды, но не блокирует принятые решения.

## 11. Роли и ответственность

- **Architecture Review Board (ARB)** — высший орган архитектурного управления (§6.1 TOR-004): утверждает ADR, изменения принципов, стандартов, моделей знаний (MM-*) и Canonical Models; разбирает междоменные архитектурные конфликты; кворум — не менее двух третей состава (временно исключён, см. раздел 10).
- **Domain Owner, Architecture Owner, Metadata Owner, Data Steward** — роли по каждому домену знаний (§5.4 TOR-004), явно поименованные в манифесте объекта; могут совмещаться одним лицом.
- **Owner артефакта** — отвечает за актуальность и качество конкретного документа (манифест KOMS).
- **Авторы и ревьюеры** — закрепляются в .github/CODEOWNERS.
- **Контрибьюторы** — вносят изменения через Issue и Pull Request.

## 12. FAQ новичка

**Где код?**
Код платформы появляется по фазам §12 TOR-004. Presentation Layer уже реализуется в отдельном репозитории CISStat_PORTAL (Next.js 14 App Router, TypeScript, Tailwind CSS, Schema.org JSON-LD — соответствует §7.10.1–7.10.2 TOR-004; детализация — приложение С). Настоящий репозиторий — архитектура и знания, а не исполняемый код.

**Чем README отличается от TOR-004, REPOSITORY.md и PROJECT_STATE.md?**
TOR-004 — нормативный источник истины («что делать»). README — правила работы с репозиторием («как работать»). REPOSITORY.md — концепция «репозиторий как система знаний» («зачем»). PROJECT_STATE.md — живой дашборд («где мы сейчас»).

**Нужно ли читать архив (ARC-*, MM-*, GOV-*, ADR-*)?**
Для начала работы — нет: их нормативное содержание поглощено TOR-004. Для понимания «почему», точных формулировок и истории споров — да (§15.4). При расхождении приоритет — TOR-004.

**Куда добавить новую модель данных?**
В каталог Data Models/ файлом `DM-XXX_Название.yaml` с манифестом по STD-001, через Pull Request. Порядок разработки — ARC-016 (§4 TOR-004): Business Concept → Knowledge Object → Ontology → Metadata Model → Logical Data Model → Physical Data Model → API Contract → Service Implementation → User Interface.

**Почему в архиве префиксы MM-* и STD-*, а в пространствах имён §5.5 их нет?**
Исторические префиксы сохранены для трассируемости ранее написанного кода и документации; целевая схема CIS-ID — §5.5 TOR-004; формальное сведение схем со STD-002 — открытый вопрос §13.2, оформляется отдельным ADR.

**Можно ли исправить чужой утверждённый ADR?**
Нет. Immutable History: либо новая редакция, либо новый ADR со ссылкой Superseded by ADR-XXX (§6.2).

**CI упал — что делать?**
Раздел 9.4: локальный прогон pre-commit, исправление по выводу, повторный коммит.
